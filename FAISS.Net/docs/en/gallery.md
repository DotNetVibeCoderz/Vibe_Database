# The Gallery

[← Documentation index](../README.md) · [Bahasa Indonesia](../id/gallery.md)

`FAISS.Net Gallery` is an Avalonia desktop application built to answer one question that a table of
numbers answers badly: **what does an approximate index actually give up, and what does it buy?**

Every screen measures a real index on real vectors — 40,000 clustered 64-dimensional vectors with
200 held-out queries — against exact ground truth computed by a flat scan. Nothing is simulated and
no number is illustrative.

```bash
dotnet run -c Release --project samples/Faiss.Net.Gallery
```

The screenshots below are generated by the app itself:

```bash
dotnet run -c Release --project samples/Faiss.Net.Gallery -- --capture docs/images
```

---

## Reading the interface

Two accent colours carry meaning everywhere in the app, and they never mean anything else:

- **Amber** — *approximate*. What an index chose to scan, the cells it probed, a result it found by
  looking at part of the data.
- **Cyan** — *exact*. Ground truth from a flat scan; the reference every approximation is measured
  against.

Across the bottom of every screen is the **probe band**: the whole database drawn as one strip,
divided into the index's cells in proportion to how many vectors each holds, with the cells the last
query probed lit in amber. It is the app's throughline. Approximate search is the decision to
deliberately not look at most of your data, and the band is that decision made visible.

## probe — watch an index skip data

![Probing an IVF index](../images/gallery-probing.png)

An inverted-file index over 40,000 vectors in 200 cells. At `nprobe = 1` the band shows 243 vectors
examined — 0.6% of the database — and the index still returns 94.6% of the correct neighbours, 27×
faster than the exact scan.

Drag the slider and three things move together: the lit fraction of the band, the recall, and the
clock. The scatter plot on the right projects the vectors onto their first two principal components
and marks one query's results — amber dots for what the index returned, cyan rings for the true
neighbours. An amber dot with no ring around it is a mistake you can point at.

The panel below the slider reports the cell distribution. A large gap between the smallest and
largest cell means the partition is unbalanced, which is the usual explanation for an IVF index with
erratic latency: `nprobe` counts cells, not vectors, and some cells are far more expensive to open.

## search — retrieve by meaning

![Searching a text corpus](../images/gallery-searching.png)

A corpus of 96 technical sentences across eight topics, embedded by hashing words into
pseudo-random directions and summing them, then indexed with `IndexFlatIP` for cosine similarity.

Results update on every keystroke, which is only reasonable because an exact scan of 96 unit vectors
takes about 1.9 milliseconds — and noticing that is itself the point. **Not every corpus needs an
approximate index.** The words the query and each result share are highlighted, so ranking quality
can be judged by reading rather than by trusting a score.

The embedding is real but simple: word overlap, not meaning. "Fast" and "quick" are unrelated
directions here. A sentence-transformer would fix that and would drop into the same index unchanged
— the retrieval half of this screen would not need a line rewritten.

## compress — shrink vectors, keep answers

![Comparing compression schemes](../images/gallery-compressing.png)

Every compression scheme in the library on the same vectors: bytes per vector, resident memory,
compression ratio, recall, and query time side by side.

Underneath, one vector is drawn twice — the original as a bone line, the decoded approximation in
amber, with the gap between them shaded. A single reconstruction-error number says a scheme lost
0.0235 per dimension. It does not say whether that loss is spread evenly or concentrated in the
dimensions that carried the signal, and those two situations rank results completely differently.
The shaded gap shows which it is.

The pattern the table makes is the useful part: 8-bit scalar quantization is 4× smaller for about
three points of recall, while 4-bit is 8× smaller and gives up nearly forty. Compression is not a
smooth dial.

## traverse — walk a proximity graph

![Traversing an HNSW graph](../images/gallery-traversing.png)

The structural counterpart of the probe screen: same data, same metrics, a completely different way
of avoiding work. HNSW builds a layered graph and walks it, so there are no cells to skip — it skips
data by never walking there. The band stays dark here, and says why.

`efSearch` is the width of the beam. The layer occupancy panel shows the hierarchy as it actually
came out: every node on layer 0, roughly one in `M` on each layer above it, five nodes at the top.
The walk starts at the single node occupying the highest layer and descends.

## measure — compare every index

![Comparing every index](../images/gallery-measuring.png)

Ten configurations built and measured in sequence against the same ground truth, each plotted on the
recall/throughput frontier as it completes.

The chart refuses to show speed and accuracy separately, because separately neither means anything.
A point that is left of and below another is simply worse — slower *and* less accurate. Points are
joined by a line only when they belong to the same sweep, so an `nprobe` ladder reads as a path
while unrelated index families stay unconnected.

The footer names the fastest configuration that reached 95% recall, which is the question most
people actually arrived with.

## dedupe — find near-duplicates

![Finding near-duplicates](../images/gallery-deduplicating.png)

Radius search asks a different question from k-nearest-neighbour: not the closest ten, but
everything within a distance — however many that is, including none. Near-duplicate detection needs
the second question, because asking for the ten nearest documents always returns ten whether or not
any of them are actually related.

Groups are formed by union-find over the pairs the radius search returns. That is also the screen's
lesson: union-find is transitive, so lowering the threshold far enough collapses the entire corpus
into one group through a chain of individually weak pairs. The app says so explicitly when it
happens. This is the classic failure of threshold-based deduplication, and the reason a threshold
should be set from measured pairs rather than guessed.

## Under the hood

The Gallery is a normal FAISS.Net consumer — it uses no internal APIs. Worth knowing if you are
reading the source:

- **`Workspace`** builds the shared data once, on a background thread. Database and queries come from
  one draw and are then split, so the queries are in-distribution. Generating them independently
  would make every approximate index look far worse than it is.
- **`ProbeBand`, `ScatterPlot`, `TradeoffCurve`, `ReconstructionStrip`** are custom controls drawn
  directly with `DrawingContext`. No charting library.
- **`--capture DIR`** renders each screen to PNG off-screen, which is how these screenshots are made
  — exact, reproducible, and free of whatever else was on the desktop.
