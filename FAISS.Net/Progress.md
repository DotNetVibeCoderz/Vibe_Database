## Performance work completed

Each measured, not assumed.

- [x] Runtime SIMD dispatch with two-accumulator unrolling
- [x] Dual threading strategy — a single query against a large database still uses every core
- [x] `ArrayPool<T>` throughout; a warm search allocates nothing
- [x] Compile-time heap ordering, so no per-candidate branch on the metric
- [x] Contiguous storage — one `float[]` for vectors, one `int[]` for the whole HNSW graph
- [x] 1.5× growth, keeping the resize peak near 2.5× the live set instead of 3×
- [x] Parallel HNSW construction with per-node locks
- [x] **Vectorized 8-bit decode** — IVFSQ search 0.535 → 0.227 ms/query (2.4×)
- [x] **Parallel OPQ Procrustes accumulation** — training 182 s → 23 s (8×)
- [x] **Pinning hoisted out of scan loops** — `Offsets`/`Steps` pinned once per list, not per candidate

## Bugs found and fixed

Logged because each one is a trap worth not falling into twice. All three are now guarded by tests or
documented in [CLAUDE.md](CLAUDE.md).

| Bug | Symptom | Cause | Fix |
|---|---|---|---|
| **Row-stride corruption** | Every query after the first returned misaligned results; padding carried label `0` instead of `-1` | Indexes clamped `k` to `ntotal` internally while the caller's buffers were sized for the requested `k` | Removed the clamp in 6 places; the heap pads short results itself. Regression test added |
| **HNSW under-connected** | recall@10 stuck at 44% regardless of `efSearch`; mean layer-0 degree 16 where `M0 = 64` | The diversity heuristic pruned without back-filling; in high dimension it rejects ~half of candidates at every step, so degree collapses exponentially | Back-fill from pruned candidates up to `M` (`keepPrunedConnections`). Degree 16 → 50, recall 44% → 98% |
| **Out-of-distribution benchmark queries** | Every approximate index looked far worse than it is; HNSW read 44% where it achieves 99% | The sample generated queries from a *second, independent* set of cluster centres | Generate `n + nq` vectors in one draw and split. Documented as rule 3 in `docs/en/performance.md` |
| **Under-warmed timing** | Scalar-quantized rows looked ~3× slower than they are | A one-query warm-up left the *threaded batch* path un-JIT-ed | Warm up on the full query set; median of 3 passes in the Gallery |

## Known gaps

Carried verbatim from [docs/en/performance.md](docs/en/performance.md), because a checklist that hides
its weak spots is not a checklist.

- **fp16 decode is scalar** — the most accurate compressed option is the slowest scan in the library
- **No precomputed IVFPQ tables** — the ADC table is rebuilt per probed cell
- **No blocked SGEMM for flat search** — the largest single performance gap against FAISS
- **GPU backend covers flat indexes only**, and has never run on real CUDA hardware
- **`IndexShards` searches shards sequentially**
- **No filtered search** — over-fetch-and-filter is the only workaround, and it under-delivers `k`
- **HNSW has no removal** — matching FAISS; rebuild or keep a tombstone set
- **`OPQMatrix` requires `dOut == dIn`** — chain a PCA for the reducing form
- **Not compatible with FAISS's file format** — by design; rebuild from source vectors

## Verification

Run before considering any change complete:

```bash
dotnet build -c Release                                              # expect 0 warnings, 0 errors
dotnet test -c Release                                               # expect 82/82
dotnet run -c Release --project samples/Faiss.Net.Samples.Console -- compare
dotnet run -c Release --project benchmarks/Faiss.Net.Benchmarks -- micro
```

Performance claims need a before-and-after from the benchmark suite. An optimization with no number
attached has not been demonstrated to be one.

Documentation changes must touch **both** `docs/en/` and `docs/id/`. Screenshots regenerate from the
app rather than being re-taken:

```bash
dotnet run -c Release --project samples/Faiss.Net.Gallery -- --capture docs/images
```
